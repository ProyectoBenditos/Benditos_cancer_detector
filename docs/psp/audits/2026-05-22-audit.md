## Hallazgos

### Críticos

#### [Crítico] H-001 — Backend imprime `score` de predicción IA en stdout (PHI en logs)

- **Evidencia**: [apps/api/app/api/v1/routers/analysis.py:192](../../../apps/api/app/api/v1/routers/analysis.py#L192) — `print(f"DEBUG analysis {upload_id} completed with score={payload.get('score')}")`.
- **Impacto**: Viola la regla PHI declarada en [apps/api/CLAUDE.md:22-30](../../../apps/api/CLAUDE.md#L22) y en CLAUDE.md raíz. `score` forma parte de `result_json` y constituye PHI. Cualquier sistema que ingiera stdout (Railway logs, journalctl, Docker logs) queda con la salida del modelo asociada a un `upload_id`.
- **Recomendación**: Sustituir por logging estructurado sin campos clínicos. Solo registrar `upload_id` truncado o un hash, código HTTP y tipo de evento. Auditar el resto de `print()` del módulo y borrar los que loguen payloads del modelo o de Supabase.
- **Relación PSP**: PSP0.1 Coding + PSP2.2 Code Review.
- **Relación SDLC**: Desarrollo + Pruebas.
- **Relación PMBOK**: Calidad + Riesgos.

#### [Crítico] H-002 — Prefijo de `SUPABASE_SERVICE_ROLE_KEY` impreso en stdout

- **Evidencia**: [apps/api/app/db/supabase_client.py:11](../../../apps/api/app/db/supabase_client.py#L11) — `print("DEBUG service role prefix:", SUPABASE_SERVICE_ROLE_KEY[:20])`.
- **Impacto**: Aunque solo se imprimen 20 caracteres, basta para inferir el formato del JWT y, combinado con otros prefijos, podría facilitar reconocimiento. No es PHI directo, pero es un secreto del sistema que viola el principio de no exponer credenciales en logs.
- **Recomendación**: Eliminar la línea por completo. Reemplazar el patrón "DEBUG ENV" del archivo de configuración por una verificación booleana silenciosa al boot y un `raise` si falta una variable obligatoria.
- **Relación PSP**: PSP2.2 Code Review.
- **Relación SDLC**: Desarrollo.
- **Relación PMBOK**: Riesgos + Calidad.

#### [Crítico] H-003 — Trazabilidad código ↔ Jira: 0/82 commits referencian `KAN-XX`

- **Evidencia**: `git log --grep="KAN-" --oneline -80` devuelve 0 resultados. Inspección visual de los 82 commits del repo confirma que ningún mensaje incluye la clave del issue.
- **Impacto**: Incumplimiento sistémico de la **Regla 1 — Todo debe ser trazable** (sección 3 de la metodología). No es posible reconstruir qué commit implementa qué issue, ni verificar que un issue "Finalizado" tenga código asociado. Auditoría bidireccional imposible. Riesgo regulatorio en un dominio clínico que exige cadena de evidencia.
- **Recomendación**: Adoptar convención obligatoria `tipo: descripción (KAN-XX)` o `tipo(KAN-XX): descripción` desde el siguiente commit. Añadir un commit-msg hook o lint que rechace mensajes sin clave Jira cuando exista un issue activo. Generar matriz inversa en `docs/psp/traceability-matrix.md` con el mapeo histórico — para los 82 commits previos puede hacerse manual, ordenándolos por sub-proyecto.
- **Relación PSP**: PSP0.1 Coding + PSP1 Planning.
- **Relación SDLC**: Desarrollo + Cierre.
- **Relación PMBOK**: Integración + Alcance.

#### [Crítico] H-004 — Cero Epics y cero `parent` en 42 issues

- **Evidencia**: Búsqueda en el resultset JQL: `"parent":` arroja 0 ocurrencias; no hay issuetype "Épica" / "Epic" / "Feature" en los 42 issues. Confirmado contra baseline 2026-05-22 (`0 / 45 con epic parent`).
- **Impacto**: Sin estructura jerárquica el backlog es plano y no permite reporting por módulo del sistema. Imposibilita agregar tiempo y avance por módulo (Ingesta, IA, API, Dashboard, Alertas, RBAC, Auditoría, Monitoreo, ETL). Reportes ejecutivos pierden granularidad.
- **Recomendación**: Crear 9 Epics (uno por módulo de §8 de la metodología), reasignar issues existentes vía edición manual en Jira (la auditoría no escribe). Documentar el listado de Epics en `docs/psp/milestones.md` con su mapeo a sub-proyectos A–E.
- **Relación PSP**: PSP1 Planning.
- **Relación SDLC**: Planificación.
- **Relación PMBOK**: Alcance + Tiempo.

#### [Crítico] H-005 — 0/42 issues con timetracking (incumplimiento Regla 2)

- **Evidencia**: Grep `"originalEstimateSeconds"|"timeSpent"|"originalEstimate":` sobre el dump JQL completo → 0 ocurrencias.
- **Impacto**: Incumplimiento total de la **Regla 2 — Todo trabajo debe tener medición**. Sin estimado vs real, no se puede calcular delta, no se puede calibrar productividad personal (núcleo de PSP), no se puede hacer post-mortem cuantitativo, no se puede medir eficiencia de revisión.

Para issues ya en "Finalizado", capturar estimaciones retrospectivas en una hoja `docs/psp/time-log.md` aunque sean aproximadas, marcándolas como `[retrospectivo]`.
